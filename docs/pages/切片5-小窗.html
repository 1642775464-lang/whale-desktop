装这一趟，揪出三个真缺陷

三个都是我自己的问题，且都是「假 ctx / 假桥永远测不出来」的那类。

这三个缺陷只在真实宿主里才现形

第一个：插件没声明 inject。 Cordis 只把 inject 里列出的服务装进插件上下文。不声明的话有个特别阴的组合——事件照样收得到（ctx.on 不走服务容器），但 sessions/agents 全是 undefined。

于是表现是：桥能看见会话在跑、能推实时数据，只有发消息时才回 session-not-found。

第二个：我把不存在的服务名写进了 inject。 想着「可选的也声明一下更保险」。结果 Cordis 会等这些服务就绪才调用 apply——一个不存在的名字，插件就永远不启动，而且不报错。

第三个：admitPromptContent 是 async。 它返回 Promise，我同步调用后把 Promise 当内容块塞进消息。宿主做 snapshotJsonValue 时遇到 Promise 返回 undefined，直接抛错——发一条消息就 500。

而宿主自己的注释写着：没有图片的 prompt「不做存储操作」。纯文本根本不需要走它，是我多加了一道没用的工序。

第一个的修法
补 export const inject；并把「没声明」与「宿主没有」两种 undefined 分开
第二个的修法
必需服务进 inject，可选服务走 ctx.get()
第三个的修法
纯文本直接自建内容块，不再调用 admission

消息流的两个坑

修「消息全渲染成助手」，实际有两层，修完第一层还是错的。

消息分流
  • 第一层 m.role
    • 桥给的是 kind，读错字段不报错，只是每条都渲染成助手
  • 第二层 user/message 的信封
    • assistant/message 用 data.message.content
    • user/message 用 data.content（没有 message 包一层）
    • 只处理了前者的字段 → 用户消息被静默丢掉

第二层更值钱：假桥里那段的信封本来就是错的，所以那条路从来没被真跑过。现在契约测试直接读桥的 messagesOf() 产出形状，不再照文档抄。
