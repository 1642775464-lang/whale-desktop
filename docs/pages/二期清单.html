先说清一件事：这些不是缺陷

每一处降级都在文档里写明了为什么，且大多配了降级行为。 比如 ＋ 添加 按钮存在（index.html 的 btnAdd），只是点了不产生副作用 —— 这正是待决清单写的「面板列出但不产生副作用」。

判断口径

文档里写明「延后 / 二期 / 能力未接通」的 = 二期范围。 文档里没写、实际又缺的 = 缺陷，那要单独修，不进这张表。

三、最值得先做的一条

历史会话唤醒提速

现在切到历史会话要等约 20 秒——因为桥只能先「唤醒」它才能读数据。 待决清单早就写了 v2 的方案：桥直读落盘，读不依赖唤醒。

我核实过：宿主的 dsh-api-session-controller 确实有读持久化的能力 （ensureSession / persisted header 相关方法），所以这条路技术可行。

这是唯一一条「现状明显影响日用、且有明确低成本方案」的项。

五、我的建议

  1. 第一步只做唤醒提速影响日用最直接、方案已定、成本最低，可独立成一片
  2. 第二步能力补齐三件侧边工作台 / ＋添加 / 按需确认，各需先定内容
  3. 第三步语音需你先定要不要
  4. 最后毛玻璃与全局热键建议明确"不做"，写进文档打消念头

第一步为什么不打包：唤醒提速有明确判据（20 秒 → 多少）， 而其余几项都卡在「内容没定」。混在一起会变成一片做不完的大切片， 违背小步迭代的原则。
