```limits
桥未启动 | max 1 | 红点 + 全部显示短横

渲染进程崩溃 | max 1 | 兜底页 + 重新加载
运行中抢发消息 | max 1 | 自动进队列，不打断
无回合时中断 | max 1 | 返回 409，不误伤
历史会话未唤醒 | max 1 | 直读落盘，照常渲染
窗口大小未知 | max 1 | 显示短横，不显示 0
用量缺失 | max 1 | 显示短横，不显示 0

```

## 四条降级原则
| 原则 | 说明 |
|---|---|
| 宁可显示短横 | 未知就是未知，禁止用 0 占位 |
| 宁可局部失效 | 一个会话读不到不影响其他会话 |
| 宁可静止 | 灰色项点击无声无息，不制造困惑 |
| 失败必有出口 | 每个断连态都给出重试路径 |

## 实测发现一 · 会话日志是逐帧压缩的
```sequence
读取器 -> 文件: 打开 session.v4.jsonl.zstd
文件 --> 读取器: 959269 字节
读取器 -> 读取器: 扫到 562 个 zstd 帧魔数
读取器 -> 读取器: 一次解压只出来 203 字节
读取器 -> 读取器: 改成按帧切片逐个解
读取器 --> 读取器: 解出 3274131 字节、967 行
读取器 -> 渲染: 23 种事件类型全部认得出
```
```callout warn 这条踩坑已写进约束
Node 原生 zstdDecompressSync 只解第一帧。解决办法是按魔数偏移逐帧解再拼接。
原生解压不可用时，回退纯 JS 解码器。以上已登记为约束 K-11 与 K-12。
```

## 实测发现二 · 上下文占用要自己算
| 事实 | 影响 |
|---|---|
| 落盘 usage 只有四字段 | 没有 cacheWriteTokens，缓存写恒为 0 |
| 没有 contextPressure 投影 | 上下文占用必须由桥自行计算 |
| totalTokens 含缓存读 | 不能当上下文占用用，会虚高 |
| usage 挂在 message.data.usage | 桥从该路径取，不是挂在 message 内 |
| 187 条消息全带 usage | 数据完整，无缺失回退场景 |

```callout ok 落地口径
上下文占用 = 输入 + 缓存读 + 缓存写，分母取会话窗口。
实测末条：983 + 92288 + 0 = 93271，窗口 1000000，占用 9.3%。
累计四桶由桥对每条助手消息求和：输入 440520、输出 92978、缓存读 12995584、缓存写 0。
```
