# 第五步 · 技术栈选型

## 结论

| 层 | 选定方案 | 理由 |
| --- | --- | --- |
| L1 运行时 | Electron 44.0.0 | 与宿主 peerDependencies 严格一致 |
| L2 宿主插件 | Cordis 插件 + Node 原生 http | 只有进程内订阅能满足 ≤300ms |
| L3 数据源 | 事件订阅为主 + 落盘 zstd 为备 | 实时靠接口、历史靠落盘 |
| L4 渲染层 | 原生 HTML/CSS/JS | 零构建链 = 零构建坑 |
| L5 通信 | HTTP + SSE | 单向推送最简解，续传免费 |
| L6 工程化 | ESLint + node:test + 自建闸门 | 零依赖可跑 |

## 总纲

> 全程零第三方运行时依赖，只用 Node 内置能力 + Electron 自身。

这不是保守。本项目的复杂度在于**与宿主的接口对齐**，不在业务逻辑。引入框架只会增加不可控面。取舍依据是「可控 > 主流」。

| --- | --- |
| 运行时依赖 | 0 |

## 四层候选与取舍

| 层 | 候选 | 选定 | 否决理由 |
| --- | --- | --- | --- |
| 运行时 | 44.0.0 / 41.10.3 / 复用 DSH.exe | 44.0.0 | DSH.exe 内嵌应用路径，无法当通用运行时 |
| 宿主 | Cordis插件 / 独立进程读落盘 / 轮询HTTP | Cordis插件 | 后两者看不见正在跑的回合 |
| 渲染 | 原生 / Vue+Vite / React+Vite | 原生 | 15 个页面撑不起构建链成本 |
| 通信 | HTTP+SSE / WebSocket / IPC | HTTP+SSE | 双向能力用不上，却要付自建续传成本 |

## 本步新识别风险

| 编号 | 风险 | 应对 |
| --- | --- | --- |
| R1 | cordis.patch.yml 被启动时整体重写 | 改动后重启验证内容存活 |
| R2 | Electron 44 zip 需联网（150MB） | 已验证可达；失败退 41.10.3 |
| R3 | 宿主无 44.x 离线缓存 | 同 R2 |
| R4 | 沙箱可能拒 npm.cmd / node -e | 写脚本文件再执行 |
| R5 | 未知事件类型被持久化层拒绝 | 只读已知类型，走容错 |

## 关键技术结论（已实测）

- 会话日志是**逐帧 zstd**：1.7MB 文件含 1148 个独立帧
- Node 原生 `zstdDecompressSync` **只解第一帧**，必须按魔数切片逐帧解
- 故**不需要任何第三方解压库**
