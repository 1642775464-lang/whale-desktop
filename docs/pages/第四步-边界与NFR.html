实测发现一 · 会话日志是逐帧压缩的

这条踩坑已写进约束

Node 原生 zstdDecompressSync 只解第一帧。解决办法是按魔数偏移逐帧解再拼接。 原生解压不可用时，回退纯 JS 解码器。以上已登记为约束 K-11 与 K-12。

实测发现二 · 上下文占用要自己算

事实 影响
落盘 usage 只有四字段 没有 cacheWriteTokens，缓存写恒为 0
没有 contextPressure 投影 上下文占用必须由桥自行计算
totalTokens 含缓存读 不能当上下文占用用，会虚高
usage 挂在 message.data.usage 桥从该路径取，不是挂在 message 内
187 条消息全带 usage 数据完整，无缺失回退场景
落地口径

上下文占用 = 输入 + 缓存读 + 缓存写，分母取会话窗口。 实测末条：983 + 92288 + 0 = 93271，窗口 1000000，占用 9.3%。 累计四桶由桥对每条助手消息求和：输入 440520、输出 92978、缓存读 12995584、缓存写 0。
