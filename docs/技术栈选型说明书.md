## 二、选型总览（先看结论）

| 层 | 选定方案 | 一句话理由 |
|---|---|---|
| L1 运行时 | **Electron 44.0.0**（离线解包，仓库根共享） | 与宿主 peerDependencies 严格一致，规避 ABI/行为差异 |
| L2 宿主侧插件 | **Cordis 插件 + Node 原生 `http`** | 桥必须跑在宿主进程内才有实时数据；不引第三方 HTTP 框架 |
| L3 桥的数据源 | **宿主服务接口（`session/event` 订阅）+ 落盘 zstd 兜底** | 实时靠接口，历史靠落盘；两条腿都有实测依据 |
| L4 渲染层 | **原生 HTML/CSS/JS（无框架无构建）** | 页面少、状态简单；零构建链=零构建坑 |
| L5 通信 | **HTTP + SSE（`text/event-stream`）** | 单向推送场景的最简解；原生 `EventSource` 直接可用 |
| L6 工程化 | **ESLint + node:test + 自建六闸门脚本** | 零依赖可跑，CI 本地托管 |

**一句话总纲**：**全程零第三方运行时依赖**，只用 Node 内置能力 + Electron 自身。这不是保守，是按「可控」准则的主动取舍——本项目的复杂度在**与宿主的接口对齐**上，不在业务逻辑上，引入框架只会增加不可控面。

## 三、L1 · 运行时（Electron 版本）

### 候选

| 候选 | 版本 | 来源 | 可控性 | 推荐 |
|---|---|---|---|---|
| **A** | **44.0.0** | GitHub Releases 离线解包 | 与宿主完全一致 | ★ **推荐** |
| B | 41.10.3 | 本机 electron Cache 已有 | 离线可用，但差 3 个大版本 | 备选（回退） |
| C | 复用 `DSH Desktop.exe` | 本机已有二进制 | 无法当纯 Electron 用（被 DSH 定制） | ✗ 否决 |

### 推荐 A：Electron 44.0.0

**理由：**

1. **与宿主严格一致**。宿主 `C:\Program Files\DSH Desktop\resources\app\package.json` 的 `peerDependencies.electron = "44.0.0"`，本机 `DSH Desktop.exe` 实测 Electron 44.0.0。同版本意味着 Chromium 渲染行为、原生窗口行为、`--no-sandbox` 语义与宿主完全一致——步骤 3/4 里那些踩坑结论（透明度、缩放、圆角）可直接沿用，不用为大版本差异重新试错。
2. **可控性已实测**。`https://github.com/electron/electron/releases/download/v44.0.0/electron-v44.0.0-win32-x64.zip` 实测 → 302 → HTTP 200，`content-length: 157455369`（约 150MB）。可达性确认，不是猜测。
3. **回退路径明确**。若下载失败，退 B（41.10.3，本机缓存已有）。**不引入 Electron 的 npm 安装链**——`electron` 包安装时会跑 postinstall 下载，且 npm 在本沙箱曾被拒，走离线解包最可控。

### 为什么否决 C（复用 DSH Desktop.exe）

该文件虽是 Electron 44.0.0 官方二进制（244654080 字节，CompanyName GitHub, Inc.），但作为 DSH 的应用入口，它内嵌了 DSH 自己的应用路径与启动参数，**无法作为通用 Electron 运行时加载我方 `main.cjs`**。且它正被宿主占用，无法复制替换。

### 落地方式（写入步骤 6 架构）

```
<仓库根>/runtime/electron.exe          # 三件套共享，单副本
<仓库根>/runtime/README.md             # 来源、版本、校验值
```

**共享而非各存一份**的原因：三件套共用同一 Electron，版本必然一致，避免三份副本漂移；同时把「运行时」与「业务代码」在目录上分开，`runtime/` 可整目录 gitignore。

## 四、L2 · 宿主侧插件（桥的宿主）

### 候选

| 候选 | 形态 | 能否拿到实时数据 | 可控性 | 推荐 |
|---|---|---|---|---|
| **A** | **Cordis 插件，跑在宿主进程内** | ✔ 能订阅 `session/event` | 高 | ★ **推荐** |
| B | 独立 Node 进程读落盘日志 | ✗ 只看到已落盘部分 | 中 | ✗ 否决 |
| C | 独立进程 + 轮询宿主 HTTP API | △ 有延迟 | 低 | ✗ 否决 |

### 推荐 A：Cordis 插件

**理由：**

1. **只有它能满足 P-5（事件到悬浮条 ≤ 300ms）**。宿主事件流 `session/event` 是进程内 EventEmitter 直发（发射点 `dsh-session/lib/index.js:1466-1473`），插件订阅后零延迟拿到；独立进程读落盘文件必然滞后于 flush 周期，且**看不见正在跑的回合**（落盘是批量的）。
2. **桥-PRD 已锁定这个形态**（F1「监听与暴露」、F6「拉窗与复用」），且 PRD 第二章专门论证了「为什么做成宿主插件而不是独立进程」。
3. **加载方式可控**。profile 的 `cordis.patch.yml` 是声明式装载清单，加一行即可挂载；**但已实测：该文件在宿主启动时会被按内存状态整体重写**（`LastWriteTime == CreationTime`，改动被冲掉）。故**不能只改文件了事**——必须走「写文件 → 重启验证内容存活 → 再验证功能」的流程，且要有失败回退记录。这是本步新识别的**实施风险 R1**。
4. **技术约束已知**：桥用 Node 原生 `http` 起服务，只 `listen('127.0.0.1', 19387)`；端口占用时明确报错不静默换端口（C-8、F-7）。

### 为什么否决 B/C

- B：桥-PRD 第 2 章已列表对比，结论是「速度、状态点全部无法实时」，直接违反 F7 实时性与 P-5。
- C：轮询要定周期，周期短则空转、周期长则违反 ≤300ms；且宿主未保证提供等价的等价查询面。SSE 是更贴合的形态。

### 关键技术决策：数据源双通道

| 通道 | 用途 | 依据 |
|---|---|---|
| **主**：`ctx.on('session/event', ...)` | 实时事件流（SSE 推送） | 进程内订阅，零延迟 |
| **备**：落盘 `session.v4.jsonl.zstd` | 历史会话渲染（F9 切会话） | 会话不在内存时唯一来源 |

**落盘读取的实现要点**（已实测，写入开发规范强制项）：

- 事件日志是**逐帧 zstd**，实测一个 1.7MB 文件含 **1148 个独立帧**（魔数 `28 b5 2f fd`）。
- Node 原生 `zlib.zstdDecompressSync(buffer)` **只解第一帧**；`createZstdDecompress()` 流式同样只出第一帧。
- **正确解法**：扫魔数偏移 → 按 `[offsets[k], offsets[k+1])` 切片 → 逐帧解压 → 拼接。
- 该结论已从「会话日志是逐帧压缩的」实测得出，**不需要第三方解压库**。

## 五、L3 · 渲染层（两个 Electron 前端的写法）

### 候选

| 候选 | 构建链 | 依赖数 | AI 友好 | 推荐 |
|---|---|---|---|---|
| **A** | **原生 HTML/CSS/JS，无框架无构建** | 0 | 高（直接可读） | ★ **推荐** |
| B | Vue 3 + Vite | 有 | 中 | ✗ 否决 |
| C | React + Vite | 有 | 中 | ✗ 否决 |

### 推荐 A：原生三件套，零构建

**理由：**

1. **页面数量与状态复杂度不支撑框架**。总计 15 个页面（P1–P15），单页状态最复杂的是小窗主界面（消息流 + 任务坞 + 命令面板），但都是**线性列表渲染**，没有深层嵌套的组件复用需求。框架解决的是「复杂状态树 + 大量组件复用」，本项目两样都不重。
2. **零构建链 = 零构建坑**。不引入 Vite/打包器，就不存在「产物路径映射错误」「HMR 与 Electron 加载协议冲突」「sourcemap 定位错位」这一类问题。步骤 3/4 已经踩够底层坑了，不在工具链上再挖一个。
3. **满足 AI 友好准则**。`.cjs`/`.js` 源码即运行代码，AI 改了直接生效、直接可读、直接可 grep；框架的编译产物与源码脱节，排查时要多一层映射。
4. **卸载产物可预期**。PRD F13 崩溃兜底页、F11 崩溃自愈都要求「渲染进程挂了要有静态兜底」——纯静态 HTML 天然满足，不依赖构建产物是否生成成功。
5. **PRD 已锁定文件布局**（小窗 PRD 第七章：`main.cjs` / `preload.cjs` / `renderer/{index.html,app.js,skin.css}`），与零构建方案完全吻合。

### 为什么否决 B/C

同样是「可控」排序的结果，不是框架不好，而是**框架的收益（组件复用、响应式）在本项目用不满，成本（构建链、依赖树、排错层）却要全付**。若后续页面数翻倍、出现大量跨页组件复用，可重新评估——记入「可迭代项」。

### 渲染层的硬约束（来自 PRD，实现时必须遵守）

| 约束 | 内容 | 违反后果 |
|---|---|---|
| `--no-sandbox` | 启动必须带 | 沙箱下窗口行为异常 |
| 显式 `app.setPath('userData', ...)` | 必须 | 让 Electron 解析默认 userData 会**原生崩溃**，退出码 `-36861`/`0xFFFF7003`，try/catch 接不住 |
| 清除 `ELECTRON_RUN_AS_NODE` | spawn 时必须 `delete` | 宿主注入了该变量，Electron 会退化成纯 node，报 `Cannot find module 'electron'` |
| 物理像素走 `GetWindowRect` | 禁用 `devicePixelRatio` 换算 | 系统缩放 113% 而 dpr 报 1，依赖 dpr 会**错 13%** |
| 不加孤儿防护 | 不要加回 | 首版教训，已移除 |

## 六、L4 · 通信协议

### 候选

| 候选 | 方向 | 断线续传 | 实现成本 | 推荐 |
|---|---|---|---|---|
| **A** | **HTTP（请求/响应）+ SSE（推送）** | `Last-Event-ID` 原生支持 | 低（Node 内置 + 浏览器内置） | ★ **推荐** |
| B | WebSocket | 需自建 | 中（要引 `ws` 或手写握手） | ✗ 否决 |
| C | IPC / 命名管道 | 不跨进程边界 | — | ✗ 否决（宿主已实测禁用命名管道） |

### 推荐 A：HTTP + SSE

**理由：**

1. **数据流是单向的**。宿主 → 客户端是事件推送（SSE 主场）；客户端 → 宿主是离散的 22 条路由请求（HTTP 主场）。WebSocket 的双向能力在此**用不上**，却要付「自建续传、自建重连、引入依赖或手写握手」的成本。
2. **断线续传是免费拿到的**。R-3 要求「带 `Last-Event-ID` 续传、断线期间事件不丢（按 seq 补齐）」——SSE 协议原生定义了这个头，浏览器 `EventSource` 自动重连并回传。WebSocket 要自己实现一套等价语义。
3. **零依赖**。客户端侧用浏览器内置 `EventSource`；服务端侧用 Node 内置 `http` 手写 `text/event-stream` 响应（就是几个 `res.write('data: ...\n\n')`）。不引 `express`、不引 `ws`。
4. **可调试性碾压**。SSE 是纯文本 HTTP，`curl` 一条命令就能看流（C3 验收正是这么测的）；WebSocket 要专门工具。

### 端口与安全（PRD 已锁定）

| 项 | 取值 | 依据 |
|---|---|---|
| 监听地址 | `127.0.0.1` 仅回环 | SEC 组 + 桥 PRD 5.1 |
| 端口 | **19387 固定**，占用则明确报错 | C-8；不静默换端口 |
| 凭证 | **不做凭证**（回环 + 本地单用户） | 桥 PRD 5.2 |
| 卸载清理 | 先关拉起的小窗，再关 HTTP 服务 | 桥 PRD 5.3，避免端口泄漏 |

## 七、L5 · 工程化工具链

### 候选与选定

| 用途 | 候选 | 选定 | 理由 |
|---|---|---|---|
| Lint | ESLint / Biome | **ESLint** | 资料最多，规则可机械化检查，零配置心跳成本低 |
| 测试 | node:test / Vitest / Jest | **node:test** | Node 24 内置，零依赖，`node --test` 直接跑 |
| 覆盖率 | c8 / 内置 `--experimental-test-coverage` | **内置** | Node 24 自带，不引第三方 |
| 构建 | 无 / Vite | **无** | L3 已定零构建，无构建步骤 |
| 密钥扫描 | gitleaks / 自建正则脚本 | **自建脚本** | 零安装；规则少而明确（见开发规范） |
| 依赖扫描 | npm audit / 自建清单 | **`npm audit` + 自建** | 本项目运行时依赖为 0，`npm audit` 只覆盖 devDeps |
| 版本控制 | Git | **Git**（本地托管） | 步骤 9 落地；当前工作区**尚非 git 仓库**（已实测） |

### 关键取舍说明

**为什么测试选 `node:test` 而不是 Vitest/Jest：**

- 本项目**运行时依赖为 0**，测试目标的绝大多数是纯函数（token 口径计算、事件折叠、路径解析、SSE 帧编码）。
- `node:test` 内置，`node --test` 一条命令跑全部，不引依赖树，**不受 npm 网络/沙箱影响**（本沙箱已出现 `npm.cmd` 被拒的情况）。
- 覆盖率用 Node 24 内置 `--experimental-test-coverage`，`c8` 也不必装。

**为什么密钥扫描自建：**

六闸门要求「密钥扫描」，但本项目**运行时依赖为 0、无 `node_modules` 运行时树**，需要扫的是自家源码里有没有硬编码凭证。规则少（API key / token / 私钥 / 连接串），正则可穷举，自建脚本零安装、可读、可改。若后续引入外部服务再评估换 gitleaks。

### 六闸门与本层工具的映射（为步骤 9 预备）

| 闸门 | 工具 | 哪一层 |
|---|---|---|
| 1 Lint | ESLint | 本层 |
| 2 覆盖率 | `node --experimental-test-coverage` | 本层 |
| 3 构建 | **无构建步骤**（零构建方案） | L3 决定 |
| 4 密钥扫描 | 自建脚本 | 本层 |
| 5 依赖扫描 | `npm audit` + 自建清单 | 本层 |
| 6 PR 审查 | 人工 + AI 自查清单 | 步骤 8 定义 |

> **注意**：闸门 3「构建」在本方案下**无对应步骤**，不是遗漏。零构建是 L3 的主动选择，闸门应改为「语法检查」（`node --check` 全量过一遍）。此项**需在步骤 9 明确记录**，避免被误判为闸门缺失。
